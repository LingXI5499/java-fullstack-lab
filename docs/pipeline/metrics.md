## 2. 返工原因分类

每次返工按下面六类之一归档，不允许写"其他"（如果确实无法归类，说明分类需要新增一类）：

| 分类 | 含义 | 典型表现 |
|---|---|---|
| SPEC | 规格不清 | 写到一半发现需求没定义、业务规则有歧义 |
| DESIGN | 设计缺失 | 表结构少了字段、接口契约与页面不一致 |
| CODE | 编码错误 | 编译失败、SQL 写错、前端状态漏了分支 |
| ENV | 环境问题 | 依赖下载失败、字符集、端口冲突、版本不匹配 |
| CHANGE | 需求变更 | 中途加需求或改规则（走变更影响卡） |
| GATE | 门禁自身误报 | 门禁规则过严或写错，需要修正门禁 |

返工分布本身就是升级依据：SPEC 多 → 强化 `jfsl-conventions` 与需求模板；
DESIGN 多 → 强化 `jfsl-data-design` / `jfsl-api-design`；
CODE 多 → 强化 `jfsl-crud-gen` 与测试骨架；GATE 多 → 修正门禁规则本身。

## 5. 怎么填这份表

1. 项目复盘（工序 24）时，从 `progress.md` 抄真实数字进第 1 节。
2. 把每类返工事件写进第 2 节对应的分类（在项目复盘里已归属）。
3. 缺陷按发现阶段统计进第 3 节。
4. 技能升级后回填第 4 节的"实际结果"——**这是判断升级是否有效的唯一依据**。
5. 如果连续两个项目的返工次数没有下降，触发一次针对流水线本身的复盘：
   找出是哪一步的产出物没有被下游真正使用，先修流程，再开工下一个项目。
